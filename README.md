# Food Log

A simple, offline-first food-tracking dashboard built with React, TypeScript and Tailwind CSS. It's a self-contained single-user tool — no accounts, no network — that persists your log to the browser's local storage.

## Features

- **Dashboard / Foods / Goals / Weekly / Monthly tabs** — a persistent tab bar switches between the dashboard, a browser of reference foods, the goals history, a weekly report, and a monthly report. All stay mounted and share one data store, so the dashboard keeps its logged entries while you browse and reflects goal changes immediately.
- **Foods page** — a **user-managed** reference library grouped into headed sections by category (Dairy/Eggs, Meat/Poultry, …), each food showing its serving size and key macros. On first load the library is **seeded once** from `src/data/proteinSources.json` into `localStorage`; after that the stored copy is the sole source of truth. You can **add a food** to any category (name, serving size, protein/carbs/calories required; fat/fiber optional), **add a category**, **edit a food** in place (its id and category preserved), and **delete** a single food or a whole category (deleting a non-empty category asks first). Tapping a food jumps to the dashboard with the add-food modal pre-filled from its macros — user foods store plain numbers, and `fat`/`fiber` flow through when present; you can adjust anything before saving.
- **Auto-fill missing macros (Gemini)** — on the Foods page's add/edit form, an **Auto-fill missing macros** button estimates a food's per-serving macros from its **name + serving size** via Google Gemini and fills **only the currently-empty** fields (protein/carbs/calories/fat/fiber) — anything you typed is left untouched. You still review the result and click **Save** as normal; nothing is written automatically. The button is **disabled** until both a name and serving size are entered, and is **hidden entirely** when no API key is configured, so the rest of the app works unchanged without one. Failures (network, quota, an unusable response) surface inline and never block manual entry. Requires `VITE_GEMINI_API_KEY` — see [Gemini auto-fill setup](#gemini-auto-fill-setup) below.
- **Quantity scaling** — when the modal opens pre-filled from a reference food, the macro fields represent **one serving** (shown read-only, e.g. `1 large`) and a **quantity** input multiplies them, so "I ate 2 eggs" or "half a cup" scales protein/carbs/calories — and any fat/fiber you add — automatically, with a live preview of the totals. Quantities allow decimals (`0.5`) and scaled macros round to one decimal place. The logged entry remembers its serving and quantity and the food-log row shows them (e.g. **`Egg — 2 × 1 large`**). A blank open from the `+` button has no quantity field and behaves as before — entered macros are final.
- **Date selector** — the app lands on the **real current date**, and a **Today** button jumps back to it. Pick any day from a clickable month-grid calendar (a popover behind the date button — visible weekdays make "a Wednesday two weeks ago" a glance-and-click) or step one day at a time (`‹` / `›`). The summary card and food log are both driven by the selected date, so they always describe the same set of entries. The current date is an injectable `today` prop (defaulting to the real clock) so tests pin a known day instead of depending on `Date.now()`.
- **Daily summary card** — the selected day's totals vs. the **goal in effect on that day** for calories, protein, fat, carbs and fiber, colour-coded by whether each goal is met. The goal shown here is read-only — it's resolved from the goal history (see below) and edited on the Goals tab.
- **Weekly report (Weekly tab)** — an optimization view over a rolling **last-7-days** window (step back/forward a week with `‹` / `›`, or jump to **This week**). Five widgets, all derived from the shared food log: a **macro-consistency line chart** (protein / carbs / fat per day, to spot weekday-vs-weekend drift), a **protein-goal streak** (days hit out of 7 plus the longest run, with a per-day pip strip), a **fiber-vs-goal bar chart** with a goal reference line, a **meal-calorie pie** showing where the week's calories concentrate (Breakfast / Lunch / Dinner / Snacks, colour-matched to the food-log headers), and a **protein-source pie** breaking the week's protein down by food group (Dairy/Eggs, Meat/Poultry, Seafood, Vegetables, Legumes, Whole Grains, Nuts/Seeds, Supplements, Other). Each logged entry's free-text description is matched against your food library to find its food group: an exact name match wins, else a **token match** (a library food whose key words — e.g. *greek*, *yogurt* — all appear in the description, so "Stonyfield Organic Greek Plain Nonfat Yogurt" still reads as Dairy/Eggs), then supplement keywords (whey, casein, collagen, protein powder/shake, …) and a few generic aliases (steak → Meat/Poultry, fish → Seafood). Anything still unresolved — including free-text *meal* names like "Breakfast Bowl" that aren't a single food — falls into **Other**. The protein-streak threshold and fiber target are **not a separate setting** — each day is judged against the **goal in effect on that day** from the Goals tab's effective-dated history, so editing your goals flows straight through. The aggregation is the pure, unit-tested `src/lib/weekly.ts`; charts are [Recharts](https://recharts.org/).
- **Monthly report (Monthly tab)** — a big-picture view over a full calendar month (step back/forward a month with `‹` / `›`, or jump to **This month**; forward navigation is clamped at the current month). Three widgets, all derived from the shared food log: **caloric and protein ceiling & floor heatmaps** — two calendar grids where each logged day is coloured against that day's goal using a **±10%** band. Calories is a budget (green = comfortably under the floor, amber = nearing the goal, red = over the ceiling); the protein grid **inverts** green/red because more is better (green = hit the goal/over the ceiling, amber = nearing it, red = missed/under the floor). Unlogged days are left neutral on both; a **top-10 most-frequent foods** list ranked by entry count (case-insensitive, across all meal types — handy for a recurring grocery list); and a **macro-ratio donut** showing the month's overall protein / carbs / fat split, colour-matched to the Weekly report's macro lines. Each heatmap day is judged against the **goal in effect on that day** from the Goals tab's effective-dated history, so a mid-month goal change is respected per day. The aggregation is the pure, unit-tested `src/lib/monthly.ts`.
- **Effective-dated goals (Goals tab)** — goals are a dated history rather than a single timeless value, so changing a goal doesn't silently re-judge past days. Each entry is a date plus a full set of five macro targets; the goal for any viewed day is the entry with the **latest effective date on or before that day** (dates before the first entry use the earliest one, so there's never a "no goal" gap). The Goals tab lists the history newest-first with a delete control per row and an **add-goal-change** form (date + the five macros, with its own validation). Editing is **add-and-delete only** — an existing entry is immutable, so an "edit" is a delete-and-re-add; adding on a date that already has an entry replaces it, and the last remaining entry can't be deleted.
- **Meal-grouped food log** — the selected day's entries grouped under Breakfast, Lunch, Dinner and Snacks, each with a **colour-coded bold header** (blue / green / purple / amber) and a **per-meal subtotal row** summing the five macros (kcal, protein, fat, carbs, fiber) below its entries. Empty meals show a friendly empty state and no subtotal.
- **Add / edit / delete entries** — a floating `+` button opens a modal form (food name, meal type and the five macros) that appends a new entry to the **selected** day. Each food row has an **edit** control that reopens the same modal pre-filled with the entry's fields (title "Edit food", "Save" button) and saves the changes in place (same `id`), and a **delete** control that removes the entry after a confirmation. Editing treats the macros as final totals — there's no quantity scaling even for an entry first logged from a reference food, and saving such an edit drops its `2 × 1 large` serving label, since hand-edited totals no longer match the serving math. All three immediately update the summary totals and the meal feed.
- **Bulk import from CSV** — an **Import CSV** button beside the `+` action opens a modal that loads a spreadsheet export of food entries **entirely client-side** (no upload). The file is parsed and validated **row by row** against the schema `Date, Meal Type, Food Description, Fat, Carbs, Protein, Calories, Fiber` (dates as `M/D/YYYY`); meal-type variants are auto-mapped (e.g. `Snack` → `Snacks`, case-insensitive). A **preview** shows how many rows are valid and lists each error with its source line and reason (bad date, unrecognised meal type, non-numeric/negative macro, missing field). On confirm only the valid rows are **appended** (existing entries for those dates are left untouched — no dedup), and the dashboard jumps to the first imported entry's date. A sample file lives at `src/data/meal-bulk-load.csv`.
- **Event log** — a small **floating log button** fixed to the bottom-right corner (visible on every tab) opens an overlay showing the app's recent activity — food/category/entry/goal changes and every Gemini auto-fill attempt (request, success, or the raw failure message). Entries are shown **newest-first** with info/warn/error colour-coding and any structured context (e.g. the food + serving sent to Gemini). A **Refresh** button re-reads the log so events written while the panel is open appear on demand. The log **persists across reloads** in `localStorage` (`foodlog:log:v1`), capped at the **last 100 entries** so it never grows unbounded. Useful for diagnosing an auto-fill error that would otherwise vanish when the form resets.
- **Local persistence** — your entries, goal history **and** reference foods are saved to the browser's `localStorage` (under versioned keys `foodlog:entries:v1` / `foodlog:goalHistory:v1` / `foodlog:foods:v1`) and reloaded on every visit, so everything survives refreshes and restarts. On a first-ever load (empty storage) the app seeds a demo day, a single default goal, and the reference-food library (from the bundled JSON); once you've made any change the seed never re-runs or overwrites your data. A pre-existing single goal from an older version (`foodlog:goals:v1`) is migrated into one history entry on load. Corrupt or absent storage falls back to the seed/defaults rather than failing.

State is persisted to `localStorage` and seeded — only when storage is empty — with example entries pinned to a fixed demo day (`2026-05-01`, in `src/useFoodLog.ts`), decoupled from the real "today" the app lands on. The `useFoodLog` hook is the single data source the app reads from (lifted into `App` so the dashboard and Goals tab share one instance): it loads from storage on mount (seeding when empty, migrating a legacy single goal when present) and writes every change straight back, going through a `FoodLogStore` interface (`src/lib/foodLogRepo.ts`) so components never touch `localStorage` directly and tests inject an in-memory fake. Goal resolution is the pure `goalsForDate(history, date)` in `src/lib/nutrition.ts`. The nutrition math lives in `src/lib/nutrition.ts`, and ISO date math in `src/lib/dates.ts`: UTC-safe `addDays` / `weekdayOf` / `isoWeekOf` and the month helpers `startOfMonth` / `addMonths` / `monthDays` (the Monthly report's calendar window), plus `todayIso` (the local current day) and the `isoToDate` / `dateToIso` helpers that bridge ISO `YYYY-MM-DD` strings to/from the calendar's `Date` values without timezone drift. The calendar itself is [React DayPicker](https://daypicker.dev/) (`@daypicker/react`). The reference-food helpers in `src/lib/foods.ts` type the JSON and normalise its mixed macro strings — ranges (`"100-110"`) take the lower bound, the `"<1"` sentinel rounds up to `1`, and anything unparseable falls back to `0`. `seedFoodsFromJson()` uses that normaliser to build the first-run library (a `Record<category, UserFoodReference[]>` of plain-number macros, each food stamped with an id) that `useFoodLog` writes to `localStorage` when the foods key is empty; thereafter the static JSON is only this seed and the stored copy is read instead. The module also holds the pure `scaleMacros` helper (and its `roundMacro` rounding rule) that multiplies a per-serving macro set by a quantity. The `FoodEntry` type carries optional `servingSize` and `quantity` fields, set only for quantity-scaled entries and omitted by seed data and manual entries.

## Stack

- [Vite](https://vite.dev/) + React 19 + TypeScript
- [Tailwind CSS v4](https://tailwindcss.com/) (via `@tailwindcss/vite`)
- [React DayPicker](https://daypicker.dev/) (`@daypicker/react`) for the calendar date picker
- [Recharts](https://recharts.org/) for the weekly report's line / bar / pie charts
- [Web Storage API](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage) (`localStorage`) for persistence
- [Google Gemini](https://ai.google.dev/gemini-api/docs) (`@google/genai`) for the optional macro auto-fill
- [Vitest](https://vitest.dev/) + [React Testing Library](https://testing-library.com/) for tests

## Gemini auto-fill setup

The Foods-page **Auto-fill missing macros** button is optional and off until you provide a Google Gemini API key:

1. Get a key from [Google AI Studio](https://ai.google.dev/gemini-api/docs/api-key).
2. Copy `.env.example` to `.env.local` and set `VITE_GEMINI_API_KEY` to your key.
3. Restart `npm run dev` (Vite only reads env files at startup).

Without the key the control is hidden and the rest of the app works normally. The estimate is requested as structured JSON from a flash-tier model (`gemini-3.5-flash`) using the food's name and serving size; all of this is isolated in `src/lib/gemini.ts`.

> **⚠️ Security — personal/local use only.** This is a pure client-side app with **no backend**, so it calls Gemini **directly from the browser** and the key is **inlined into the shipped bundle** — anyone who loads a deployed build can read it. Only set the key for a personal/local build. If this is ever deployed for others, the secure alternative is a **server-side proxy** that holds the key and exposes a narrow endpoint; that's a known limitation and out of scope here. Vite only inlines build-time vars prefixed with `VITE_` (it does **not** read `process.env` in the browser), which is why the key is named `VITE_GEMINI_API_KEY` and passed explicitly to the SDK.

> **Possible follow-up.** [Google Search grounding](https://ai.google.dev/gemini-api/docs/google-search) could make estimates reflect looked-up values, but the `googleSearch` tool can't currently be combined with a strict `responseSchema` in one call, so the structured-JSON path is used on its own for now.

## Persistence

The log lives in the browser's `localStorage` under three versioned keys, `foodlog:entries:v1` (the entries array), `foodlog:goalHistory:v1` (the effective-dated goal history — a sorted list of `{ effectiveDate, goals }`) and `foodlog:foods:v1` (the reference-food library — a `Record<category, UserFoodReference[]>`). The `useFoodLog` hook loads them on mount and writes back on every change, all behind a small `FoodLogStore` interface (`src/lib/foodLogRepo.ts`) so the storage details stay isolated and tests can inject an in-memory fake. Each key is shape-validated on read, so a tampered or wrong-shaped value falls back to the seed/defaults instead of crashing a consumer. A fourth key, `foodlog:log:v1`, holds the app **event log** — a capped (last 100) list of `{ ts, level, message, context? }` entries written by the framework-free `src/lib/logger.ts` and shown by the floating `LogViewer`; it's read/written directly (outside `FoodLogStore`) so it can be called from the framework-free Gemini client too, and a corrupt value degrades to an empty log.

Seeding follows a **seed-when-empty** rule: on a first-ever load (no key present) the demo day, a single default goal entry, and the reference-food library (built from the bundled JSON) are seeded and immediately written back, so once any data exists — even an empty log after you delete everything — the seed never re-runs or overwrites it. **Migration:** if there's no goal history but a legacy single goal (`foodlog:goals:v1`, from before goals were dated) exists, it's converted into one history entry effective at a sentinel epoch date so it applies to every day; the legacy key is read-only and left in place. Malformed or absent JSON is treated as empty and falls back to the seed/defaults rather than throwing. There are no accounts and no network calls; the data is local to the browser profile.
